# LotScope Workbench — Candidate Intervention Architecture

Date: 2026-09-13
Status: design direction / implementation contract
Repository: `aerovista-us/lot-assessment`

## Decision

Workbench remains automation-first. It must search many options, apply hard gates, rank the strongest distinct solutions, and reduce the field before a staff member is asked to intervene.

Human intervention is a second-layer capability for candidates that are fundamentally sound but still have local or potentially repairable blockers. Staff may change geometry and design intent, but may never manually mark a gate as PASS. Every edit returns to the same validation pipeline.

North-star flow:

`Lot + rules + program -> broad automated search -> gate/rank/deduplicate -> recommended + acceptable candidates -> staff intervention -> exact re-evaluation or bounded search around edit -> compare -> select passing option -> freeze -> package/present`

## Domain hierarchy

The persistent model should be:

`Project -> Lot -> Design -> Revision -> Evaluation`

- **Project** — customer/job container.
- **Lot** — parcel, survey, frontage, rules, provenance and site assumptions.
- **Design** — meaningfully different site topology or concept.
- **Revision** — a bounded variant of a design.
- **Evaluation** — immutable machine evidence generated by a specific engine/rules revision.

A design/revision is not a screenshot. It is a portable collection of editable components plus lineage and evidence.

## Candidate classes

The pipeline owns candidate status. Staff may choose what to review, branch or present, but cannot set validation status.

Primary states:

1. `DRAFT`
2. `QUEUED_FOR_EVALUATION`
3. `EVALUATING`
4. `REJECTED`
5. `PARTIAL_FAIL`
6. `ACCEPTABLE_FOR_INTERVENTION`
7. `PASS`
8. `PROMOTION_READY`
9. `FROZEN`
10. `ARCHIVED`

`ACCEPTABLE_FOR_INTERVENTION` is intentionally not PASS. It means the candidate retains enough sound parcel/program/topology value that a human adjustment is worth evaluating.

Candidates with fundamental parcel, program or impossible-topology failures should remain documented but should normally not enter the intervention queue.

## Automated exploration stays first

A new lot should begin with automated exploration across multiple topology families and bounded variations. Workbench should continue to evaluate placement, setbacks, program capacity, vehicle circulation, pavement, garage geometry and repair actions without requiring the staff member to design first.

The system should not expose hundreds of near-duplicate raw solver outputs. It should cluster/deduplicate them into a smaller set of meaningfully different designs and surface:

- **Recommended** — passing, high-ranked candidates.
- **Acceptable for intervention** — promising candidates with localized blockers.
- **Rejected / history** — retained for evidence and future reference.

## Component-based candidate model

Each candidate should be assembled from individually addressable components rather than a flat image. Initial component types:

- parcel polygon and frontage edges;
- setback/buildable envelopes;
- home masses;
- garages/accessory structures;
- stalls / parked vehicle poses;
- garage doors/openings;
- driveway segments and control paths;
- pavement/apron polygons;
- circulation hint/control paths;
- annotations and staff notes.

Component properties must be serializable. Depending on type, properties include position, dimensions, rotation, vertices, door face/location/width, lock state, move bounds and provenance.

## Staff intervention contract

A staff member opens an acceptable candidate and chooses **Create Intervention**. Workbench creates a branch before any geometry is changed; the parent candidate remains immutable.

The first editor only needs a deliberately constrained toolset:

- select;
- move;
- resize/re-proportion;
- rotate;
- edit garage opening;
- edit pavement/apron vertices;
- edit route control points / sketch a route hint;
- lock/unlock allowed dimensions or position;
- annotate.

As soon as geometry changes, prior evidence becomes `STALE`. Existing PASS badges must never remain visually authoritative after an edit.

Staff actions are limited to:

- save checkpoint;
- evaluate this edit;
- explore around this edit;
- discard;
- branch variant;
- create new design from this candidate.

There is no manual PASS control.

## Variant versus new design

Workbench should distinguish a bounded revision from a topology change.

A **variant/revision** preserves the underlying concept and changes bounded geometry — for example, rotating/repositioning one garage while keeping the same overall access strategy.

A **new design** changes the site topology — for example, replacing a shared-driveway concept with independent access, materially reshaping a primary building mass, or changing the relationship among structures and circulation.

The UI should suggest `Save as new design` when edits cross a topology threshold, while preserving the parent lineage.

## Evaluate this edit

`Evaluate this edit` tests exactly what the staff member drew. It reruns the current hard gates, including as applicable:

- parcel/buildable containment;
- setbacks;
- structure overlap/separation;
- required program and stall capacity;
- garage-door crossing;
- full-body vehicle collision clearance;
- minimum turning radius;
- companion parked vehicles;
- independent inbound circulation;
- independent outbound circulation;
- pavement containment;
- downstream room/program gates;
- evidence/report generation.

A staff edit is merely a candidate until this pipeline evaluates it.

## Explore around my edit

`Explore around my edit` is the bridge between human intuition and automated optimization.

Workbench converts selected staff changes into bounded solver variables. Example:

- Garage B rotation: 30–40 degrees;
- X/Y translation: +/-3 ft;
- pavement expansion: 0–8 ft;
- selected route control points movable;
- garage size locked at 22x22.

The solver then creates and ranks descendants around the staff proposal using the same hard gates. The staff member is supplying a new search region, not replacing the solver.

## Evidence ownership and history

Every evaluated candidate remains documented, including failures and partial failures. Each record should preserve:

- what passed;
- what failed;
- measured margins;
- blocker class;
- likely repair classes;
- engine/schema revision;
- rules/provenance snapshot;
- parent/child lineage;
- staff note explaining design intent.

This turns failed work into reusable design knowledge rather than disposable output.

## Candidate library and lineage

The Candidate Library is a first-class Workbench surface. It should support filtering by status, design family, intervention type, topology and evidence result.

A lineage view should make branching obvious, for example:

```text
Design 4
|- 4A route/pavement studies
|- 4B rotated-garage family
|  |- 4B.1 30 deg
|  |- 4B.2 35 deg
|  `- 4B.3 35 deg + apron
`- Design 5 (new topology derived from earlier work)
```

## Import, export and checkpoints

Candidates should support lightweight internal checkpoints plus portable export/import.

Canonical editable package target: `*.lotscope.json`, with an optional `*.lotscope.zip` bundle when evidence/render assets are included.

An editable package should preserve components, lot/rules snapshot, design/revision IDs, lineage, staff notes, historical evaluation, engine/schema version and evidence manifest.

Import options:

- Open as copy;
- Create variant;
- Create new design.

Imported historical PASS/FAIL results are retained as history but are never trusted as current evidence. Imported candidates enter `REVALIDATION_REQUIRED` until the current pipeline reruns them.

Human-facing exports such as PDF/SVG/PNG reports are separate from the editable Workbench package.

## Pondy example vocabulary

Use the current Pondy work as a reference for lineage semantics:

- **Design 4** — current shared-driveway/two-detached-garage baseline.
- **Design 4B** — rotated Garage B family; same underlying concept, new orientation geometry.
- **Design 5** — materially different topology, including a different Home B/access relationship and no longer the same shared-driveway concept.

These labels are examples, not hard-coded product logic.

## Guardrails

1. Hard gates remain hard.
2. Staff cannot set PASS.
3. Any geometry edit invalidates prior current evidence until rerun.
4. Public LotScope only claims capabilities promoted from validated Workbench/shared-engine behavior.
5. Human route sketches are hints/control paths, not proof of vehicle feasibility.
6. Rotation is only promoted where walls, doors, parked poses, setbacks and collision geometry are rotation-aware.
7. Candidate history is append-oriented; original evaluated states are not silently overwritten.
8. Promotion/freeze always records the exact evaluation and engine/rules revision used.

## Success criteria

This architecture is successful when a staff member can start with a new lot, let Workbench search broadly, review a small set of distinct strong candidates, branch one promising partial failure, move/resize/rotate individual components, submit the edit back through the same hard-gate pipeline, optionally let Workbench optimize around that human idea, compare descendants, and freeze a passing preferred candidate without losing any earlier evidence or design history.
